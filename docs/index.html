Parte 1 · Wearables

¿Qué es un wearable?

  • Dispositivo electrónico que se porta en el cuerpo y mide de forma continua
  • Tres capacidades básicas: sensar → procesar → comunicar
  • Del laboratorio al cuerpo: la medición deja de ser puntual y se vuelve personal y continua

1 min. Enfatizar la diferencia con un sensor fijo: el wearable sigue a la persona.

Tipos de wearables (por para qué sirven)

  • Bienestar y deporte: pasos, sueño, entrenamiento
  • Salud clínica: monitoreo de glucosa, ECG, detección de caídas
  • Seguridad laboral: fatiga, exposición a calor, gases
  • Investigación: instrumentar a las personas, no solo a los edificios
    • … y aquí entra el confort térmico

Caso IER: smartwatch para confort térmico

  • Motivación: los modelos adaptativos de confort requieren encuestas + mediciones fisiológicas, y no existía un ecosistema abierto que integrara ambas en un solo wearable
  • Hardware abierto (GPLv3), ~49 USD, sin PCB a la medida:
    • XIAO ESP32C3 (WiFi + BLE)
    • GY-906 (MLX90614): temperatura de piel por infrarrojo, ±0.5 °C
    • MAX30102: frecuencia cardiaca (fotopletismografía)
    • Pantalla táctil redonda XIAO (240×240) + motor vibrador
    • Carcasa impresa en 3D, batería LiPo (~8 h)

1.5 min. Destacar: componentes comerciales de bajo costo, diseño reproducible, archivos en Zenodo (doi:10.5281/zenodo.14835096).

¿Qué recolecta el smartwatch?

Encuesta simplificada de confort (cada hora, con alerta vibratoria):

  • Aislamiento de ropa (clo)
  • Actividad metabólica (met)
  • Ubicación
  • Sensación térmica y aceptación térmica

Mediciones fisiológicas:

  • Temperatura de piel en la muñeca
  • Frecuencia cardiaca

Todo se publica en tiempo real a una plataforma IoT (ThingsBoard, open source)

→ base de datos robusta para modelos adaptativos de confort térmico

1.5 min. La interfaz de encuestas está hecha con LVGL en la pantalla táctil. Sensores calibrados contra instrumentos de referencia (termómetro AET-R1B1, oxímetro Yonker YK-81C). Este dispositivo ya es, en sí mismo, un nodo IoT: puente perfecto a la parte 2.

Parte 2 · IoT, en breve

Internet de las Cosas en una lámina

  • Objetos cotidianos con sensores, cómputo y red
  • En el ambiente construido: monitoreo de temperatura, CO₂, ocupación, energía
  • El smartwatch ya recorre este camino completo: ESP32C3 → WiFi → ThingsBoard

1.5 min. Presentar el flujo clásico: sensar → transmitir → almacenar → actuar.

El ESP32: el caballo de batalla

  • Microcontrolador con WiFi y Bluetooth integrados
  • Cuesta ~100 pesos
  • Se programa con Arduino / MicroPython
  • Lee sensores y acciona salidas (relés, LEDs, motores)

1 min. Es la pieza que usaremos en la demo.

Lo que el IoT clásico no resuelve

  • Cada plataforma tiene su app, su dashboard, su API
  • Interactuar requiere programar o usar interfaces rígidas
  • Dependencia de la nube: latencia, privacidad, costo, conectividad

→ ¿Y si pudiéramos simplemente hablarle a nuestros dispositivos?

Parte 3 · IA + IoT: del sensor al agente

La IA no es un lugar: es una cadena

Escalón Energía Ejemplo
En el sensor µA IMU ST LSM6DSOX: árbol de decisión integrado; clasificar actividad agrega ~13 µA
En el MCU mW ESP32-S3: instrucciones vectoriales + ESP-DL / TFLite Micro (INT8)
Con microNPU mJ → µJ Arm Ethos-U55: MobileNetV2 de 624→8 ms y 228→3 mJ; MAX78000: 251 µJ por palabra clave
En el SoC del reloj — Apple S9: Neural Engine → Siri procesada en el dispositivo
En el gateway / laptop W LLMs locales y agentes (nuestra demo)

Cada eslabón hace lo mínimo necesario y pasa al siguiente solo lo que importa.

2 min. Esta es la lámina conceptual clave para esta audiencia. Aclarar que las cifras de Ethos-U55/MAX78000 son benchmarks de fabricante en modelos favorables; la tendencia la confirman estudios independientes.

Reglas de diseño: energía y memoria

  • La energía por inferencia ≈ número de operaciones: “correr rápido y dormir”
  • El límite real suele ser la SRAM (256–512 kB), no el cómputo → cuantizar a INT8, podar, preferir modelos pequeños (1D-CNN, árboles)
  • La radio cuesta más que la inferencia local → transmitir eventos y clases, no señales crudas

1 min. Esto justifica decisiones del smartwatch: procesar en el dispositivo y publicar datos ya digeridos a ThingsBoard.

¿Qué aporta un LLM al IoT?

  • Lenguaje natural como interfaz: “¿cuál es la temperatura?, prende el ventilador”
  • Interpretación: convertir series de datos en explicaciones y decisiones
  • Agentes: el modelo no solo responde, actúa — invoca herramientas

Formas de integrarlo:

  1. LLM en la nube (asistentes comerciales)
  2. LLM local en una computadora junto al dispositivo ← nuestra prueba de concepto
  3. Modelos pequeños en el propio microcontrolador (TinyML, aún limitado)

1.5 min. Distinguir claramente: el LLM no corre en el ESP32; corre al lado, y el ESP32 le presta sus “manos y sentidos”.

Tool calling: las manos del modelo

  • El modelo recibe una lista de funciones disponibles y decide cuándo llamarlas
{
  "name": "leer_temperatura",
  "description": "Lee el sensor de temperatura del ESP32",
  "parameters": {}
}
  • Usuario: “¿hace calor en el laboratorio?”
  • LLM → llama leer_temperatura() → ESP32 responde 29.4 → LLM: “Sí, hay 29.4 °C…”

1.5 min. Este es el concepto clave de la plática: el LLM decide, el microcontrolador ejecuta.

Los LLMs no saben leer series de tiempo

  • Darle números crudos a un LLM produce errores narrados con confianza
  • Lo que sí funciona (estado del arte 2025–2026):
    1. El agente genera código para analizar los datos (PHIA, Nature Communications 2026)
    2. Modelos fundacionales de sensores convierten la señal en contexto (PH-LLM, Nature Medicine 2025; LSM de Google: 40 millones de horas de datos de wearables)
  • Moraleja: el LLM decide y orquesta; las herramientas miden y calculan → el mismo principio de nuestra demo

1 min. Conecta la demo casera con la frontera de investigación: es el mismo patrón a distinta escala.

MCP: hacia una interfaz universal agente ↔︎ IoT

  • Model Context Protocol: estándar abierto para exponer herramientas a un LLM (el “USB” de los agentes)
  • ThingsBoard ya tiene servidor MCP oficial: consultar dispositivos, telemetría y alarmas en lenguaje natural
  • El ESP32 puede ser servidor MCP (JSON-RPC sobre HTTP, o MCP sobre MQTT)
  • Nuestra demo serial implementa el mismo patrón en versión mínima; migrarla a MCP es el paso natural

1 min. Posible gancho: “el smartwatch publica a ThingsBoard, y ThingsBoard ya habla con agentes” — el ciclo completo wearable → IoT → agente existe hoy con piezas open source.

Arquitectura de la prueba de concepto

  • Todo corre sin nube: modelo local + comunicación serial
  • El ESP32 expone sus funciones; el modelo las invoca según la conversación

¿Qué tan pequeño puede ser un LLM?

  • Laptop / PC: modelos de 7–14B conversan con fluidez (nuestra demo)
  • Raspberry Pi 5: TinyLlama 1.1B ≈ 14 tokens/s — suficiente para un agente simple
  • ESP32-S3: un modelo de 260K parámetros corre dentro del chip a ~22 tokens/s… pero solo genera cuentos infantiles
  • El agente útil vive hoy en el gateway; el microcontrolador presta sensores y actuadores

1 min. Cifras de benchmarks comunitarios (llama.cpp/Ollama), cambian con cada versión. El punto no es el número exacto sino los órdenes de magnitud.

Consideraciones y límites

  • Latencia: un LLM local responde en segundos, no milisegundos
  • Confiabilidad: puede elegir mal la herramienta o narrar con confianza datos erróneos
  • Seguridad: dar escritura a un agente (accionar salidas) amplía la superficie de ataque — p. ej., inyección de prompts
  • Privacidad: los datos fisiológicos son datos personales sensibles
  • A favor: inferencia local = privacidad, sin costos de API, funciona sin internet

1 min. Honestidad técnica: es una prueba de concepto, no un producto. Mitigaciones: permisos mínimos (API key de solo lectura), TLS en MQTT, validar qué tools se exponen.
